## Trabajo realizado

### 1. Merge de las 3 PRs apiladas — incidente con la rama base de #277

Al hacer `gh pr merge 276 --squash --delete-branch`, GitHub cerró
automáticamente la PR #277 (su base era la rama de #276, recién borrada) —
comportamiento estándar de GitHub al borrar una rama que es base de otra PR
abierta, no un fallo de la herramienta. La rama origen de #277
(`feature/library-audit-5-scanner-stale-hash`) seguía intacta con todos sus
commits, así que no hubo pérdida de trabajo: se recreó como **PR #279**,
apuntando directamente a `develop`. Se rebaseó sobre `develop` (git
descartó solo el commit ya aplicado vía el squash de #276 —
`--reapply-cherry-picks` no hizo falta). Para #278 se aprendió la lección:
se reapuntó su base a `develop` con `gh pr edit --base` **antes** de borrar
la rama de #279, evitando el mismo cierre en cascada.

Al rebasar la rama de #278 sobre `develop` apareció el primer `Lint (ruff)`
real que corría contra este código — las PRs apiladas nunca habían pasado
por el workflow de CI porque su base no era `develop`. Fallo de formato
(`ruff format`), corregido con `ruff format src tests` y commit adicional.

**Resultado**: #276, #279 (recreada), #278 mergeadas a `develop` en orden,
1129/1129 tests en verde en cada paso.

### 2. Bug real encontrado durante la ejecución: `UnicodeEncodeError` en `decompress`

Documentado como `LIBRARY-AUDIT-7` en `backlog.md`. El primer intento de
`decompress` (dry-run) contra `E:\Carpetas anbernic` crasheó a mitad de
biblioteca — nombres de ROM reales con caracteres fuera del codepage
`cp1252` de la consola de Windows (ej. `├`, dibujo de caja) rompían
`print()` en `cli.py:1190`, incluso con la salida redirigida a fichero.
Causa raíz: Python usa el codepage de consola para `stdout` pase lo que
pase con la redirección. Fix de una línea en `main()`: reconfigurar
`sys.stdout`/`sys.stderr` a UTF-8 con `errors="replace"` al arrancar, cubre
todos los subcomandos de golpe (no solo `decompress`) — mismo patrón que el
fix de la flecha Unicode del `Día51`, pero esta vez en datos reales de
usuario, no en texto fijo del código. PR **#280**, rama
`fix/cli-stdout-utf8-encoding`, mergeada a `develop`.

Detalle técnico no obvio descubierto en el proceso: cuando `stdout` está
redirigido a fichero, Python usa buffering por bloques mientras que
`stderr` se escribe sin buffer — así que en un crash a mitad de ejecución,
el orden de las líneas en el log mezclado (`2>&1`) **no refleja el orden
real de ejecución**: el traceback aparece intercalado antes de líneas de
`stdout` que en realidad se imprimieron (y ejecutaron) antes de él, solo
que su flush a disco quedó pendiente hasta el cierre del proceso.

### 3. Ejecución real contra `E:\Carpetas anbernic`

1. `rommgr decompress "E:\Carpetas anbernic" --apply` (tras el fix) —
   **29.643 descomprimidos**, **47.132 saltados**, **2 fallidos**
   (`Breath of Fire III (USA).zip`, `Spyro 2 - Ripto's Rage! (USA).zip` —
   `ZIP inválido: File is not a zip file`, ficheros dañados preexistentes
   en disco, no relacionado con el fix — pendiente revisión manual o
   re-descarga).
2. `rommgr scan "E:\Carpetas anbernic"` — 112.349 archivos vistos, 0
   errores.
3. `rommgr resolve-duplicates --apply` — dry-run mostró **18.986 grupos
   totales** (10.403 arcade excluidos intencionalmente, 8.583 de consola,
   814 con conflicto de nombre resueltos aparte vía `apply_ra_conflicts`)
   → aplicado: **10.021 archivos descartados** (papelera, no borrado
   permanente), 0 errores. El número de grupos fue mayor que la estimación
   del `Día51` (2.929) porque `decompress` generó duplicados nuevos
   (ZIP original + fichero extraído).
4. `rommgr scan "E:\Carpetas anbernic"` de confirmación — 102.328 archivos
   vistos (112.349 − 10.021, cuadra exacto con los descartados), 0
   errores.
