# Retro Vault — Día 28 (roadmap) — UX no-técnica (Phase 4)

## Contexto

El **roadmap de arquitectura (ARC) quedó cerrado en el Día27**: JobManager
centralizado, `AppConfig` partido en dataclasses por dominio y la lógica de negocio
de duplicados extraída a `services/`. PRs #22–#29 mergeadas. `develop` va 52 commits
por delante de `main` (release a estable aún **pendiente** — ver nota al final).

Con la base sólida, el Día28 ataca el **Phase 4 — Non-technical UX** del roadmap:
hacer la app usable por alguien no técnico. Cinco tareas independientes
(`PHASE4-1..5`), una rama por tarea → PR a `develop`.

> Regla de trabajo: `rommgr plan` antes de `apply`; sin deps de runtime (solo
> stdlib); cambios de UI no rompen compatibilidad con el backend. CI (ruff + pytest)
> + CodeRabbit en cada PR.

## Desglose por rama

### `feature/phase4-1-readable-errors` — PHASE4-1 (🟡 medio)

Hoy un fallo no controlado en un handler revienta como traceback/500 sin contexto.
Objetivo: respuesta JSON uniforme `{ "error": "<mensaje legible en español>" }`
con código HTTP correcto, y el traceback solo al log (no al usuario).

- [ ] 4-1a — Auditar `router.dispatch()` / `make_handler` en `web/server.py`:
  ¿hay un punto único donde envolver la ejecución del handler en try/except?
- [ ] 4-1b — Middleware/wrapper central: captura `Exception`, loggea el traceback
  (`logging_utils`), responde `_send_error(500, mensaje_legible)`. Mapear errores
  comunes (FileNotFound, PermissionError, sqlite) a mensajes claros.
- [ ] 4-1c — Revisar handlers que ya devuelven `{"error": ...}` ad-hoc para no
  duplicar; dejar el wrapper como red de seguridad.
- [ ] 4-1d — Test: un handler que lanza excepción devuelve 500 + JSON legible, y
  el secreto/traza no se filtra al cliente.

### `feature/phase4-5-rename-jargon` — PHASE4-5 (🟢 bajo)

Cambios de copy en la UI. Bajo riesgo, alto impacto percibido.

- [ ] 4-5a — Inventario de jargon en `partials/*.html` y `app.js` (DATs, SHA1,
  match, CRC, ROM set…). Decidir glosario: "DATs"→"Base de datos de juegos",
  "SHA1 match"→"Identificación automática", etc.
- [ ] 4-5b — Reemplazo + mantener términos técnicos donde el usuario avanzado los
  espera (Settings → Catálogos). Apoyarse en la skill `/localization-pass`.
- [ ] 4-5c — Repaso visual de cada tab para que el copy quede coherente.

### `feature/phase4-2-contextual-help` — PHASE4-2 (🟢 bajo)

- [ ] 4-2a — Componente tooltip reutilizable (CSS-only o `data-tooltip`) en `app.css`.
- [ ] 4-2b — Icono `?` con descripción por sección (1 frase). Reusar las descripciones
  del `TABS` config (también alimenta DESIGN-11 si se retoma).
- [ ] 4-2c — Colocar tooltips en los puntos de fricción detectados (apoyarse en la
  skill `/ui-audit` o el agente `ux-reviewer`).

### `feature/phase4-3-responsive` — PHASE4-3 (🟢 bajo)

- [ ] 4-3a — Media query `@media (max-width: 480px)` en `app.css`: sidebar colapsable,
  tiles a 1 columna, touch targets ≥44px.
- [ ] 4-3b — Verificar tabs principales en viewport estrecho (DevTools responsive +,
  si hay consola, navegador del RG556).

### `feature/phase4-4-windows-toasts` — PHASE4-4 (🟠 alto — investigar primero)

⚠️ **Restricción dura: sin dependencias de runtime (solo stdlib).** No se puede usar
`win10toast`/`plyer`. Opciones a evaluar en 4-4a antes de implementar:

- [ ] 4-4a — Spike: toast nativo sin pip. Candidatos: (a) `subprocess` → PowerShell
  con `Windows.UI.Notifications` (XML toast); (b) `ctypes` + Shell_NotifyIcon (tray
  balloon — ya hay tray httpd en `state.py`). Elegir el que no añada deps ni rompa
  en headless.
- [ ] 4-4b — Helper `notify(title, message)` aislado (no-op si no es Windows o falla).
- [ ] 4-4c — Engancharlo a los eventos: `cable_sync`/auto-sync completado e inbox
  detectado (hooks en `cable_sync_daemon.py` / inbox watcher, vía `JobManager.finish`).
- [ ] 4-4d — Test: el helper degrada con gracia (no lanza) cuando la notificación falla.

## Orden recomendado

1. **PHASE4-1** (errores legibles) — base transversal; mejora el resto al instante y
   reduce sustos durante el desarrollo de las demás.
2. **PHASE4-5** (jargon) — trivial, gran impacto percibido, sin riesgo.
3. **PHASE4-2** (ayuda) + **PHASE4-3** (responsive) — cosméticos, se pueden encadenar.
4. **PHASE4-4** (toasts) — al final: es el de mayor incógnita técnica (spike primero);
   si el spike no da una vía stdlib limpia, se aparca y se documenta el porqué.

**Estimación:** 4-1 ≈ media jornada · 4-5 ≈ 1–2 h · 4-2 ≈ 2–3 h · 4-3 ≈ 2 h ·
4-4 ≈ incierto (spike + impl).
